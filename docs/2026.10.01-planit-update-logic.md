# PlanIt update logic — how records change over time

**Date:** 2026-10-01
**Question:** can we assume applications never update in place (a new entry appears
later referencing the old one), making historical re-fetches unnecessary?
**Answer:** **No — the data disproves it.** Records mutate in place; a rolling
14-day window alone will miss most state transitions.

## Evidence (from data/ledger.sqlite, 15,914 rows across 9 boroughs)

- 15,898 distinct `(authority, reference)` pairs; only **16 duplicated pairs**,
  and **none** are lifecycle updates. All 16 are the same application listed
  under two uids at the *same* start_date/decided_date — e.g. Tower Hamlets
  `PA/26/01204` vs `PA/26/01204/NC` (plain ref + sub-type ref double-listing).
- **0** duplicated pairs show a state transition (e.g. Undecided → Permitted).
- Therefore: one PlanIt record (`name` = uid) mutates its `app_state`,
  `decided_date`, `decision`, `n_documents`, etc. as the council processes it.
  This is also what the ledger's watch→lead transition detection relies on
  (see `run()` in pam/main.py) — and why the 2026-10-01 fix to refresh all
  mutable fields on upsert matters.

## Implication for run strategy

- Typical decided_date − start_date is weeks to months, so a 14-day incremental
  window only catches applications *registered* in the last fortnight — it misses
  decisions on anything registered earlier (the majority).
- **Recommended cadence** (not yet implemented):
  - **Daily:** 14-day window, all states — fresh volume. Cheap (few pages/borough).
  - **Weekly or monthly:** `app_state=Undecided` re-fetch over a deep window
    (e.g. 12 months) per enabled borough. Few records (only open cases),
    ledger dedupes, state changes surface as lead events via existing logic.
  - Suggested interface: a `--refresh-watch` flag that overrides the window and
    restricts to watch_states. Deferred — implement when scheduling is set up.

## New applications vs updates

- Genuinely new applications (amendments, resubmissions) DO arrive as new records,
  but with a **new reference** (e.g. `2026/1234/FUL` after `2025/9876/FUL` on the
  same site) — PlanIt does not carry a "supersedes" field.
- Site-level linkage is possible via the new `uprn` column (populated for ~37%
  of rows so far) or address matching — a possible v2 feature for "this site had
  a prior application" context on leads.

## Related notes

- All boroughs are fetched and stored identically; only `Trees` app_type is
  dropped pre-storage by config (`exclude_app_types`) — everything else is
  archived, including full raw `other_fields_json`.
- Rate limiting dominates long runs: ~1h per borough for a 3-year backfill
  (~6k records), ~85% of it 429 Retry-After waits (Islington 2026-09-30,
  logs/2026.09.30-islington-backfill.log).
